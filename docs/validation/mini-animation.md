# Original 11×11 Mini native animation

Tracks [AdrieanKhisbe/timebox-studio#20](https://github.com/AdrieanKhisbe/timebox-studio/issues/20) and [AdrieanKhisbe/timebox-studio#14](https://github.com/AdrieanKhisbe/timebox-studio/issues/14).

## Sourced format and conservative policy

The original Mini implementation is pinned to hass-divoom commit [`479d728d1a414a8a9e880bd801fe5c4a6956df53`](https://github.com/d03n3rfr1tz3/hass-divoom/blob/479d728d1a414a8a9e880bd801fe5c4a6956df53/custom_components/divoom/devices/timeboxmini.py). `TimeboxMini.maxframes` is 12. Its `process_frame`, `make_framepart` and `send_frames` encode one whole 11×11 RGB444 frame per command:

```text
49 00 0A 0A 04 index delay100ms RGB444[182]
```

Indices start at zero. There is no Evo stream-size, palette/reset or stream-chunk header. The ordinary length/sum16 envelope is OldMode escaped, including reserved bytes in length, data and checksum. A single source frame follows the reference's static `44 00 0A 0A 04 RGB444` path, with no index/delay field. Its structured `playback` is `static`, `effective_duration_ms` is zero and a diagnostic explains that timed playback is not applied; it is not a timed animation or a finite-loop promise.

The [independent original Mini integration's animation instructions](https://github.com/mathoudebine/homeassistant-timebox-mini#animation) require a common frame delay and report a 200ms minimum. The hass encoder represents delay in 100ms units, capped at 255, but does not establish that 100ms playback or unequal frame delays work on the hardware. Accordingly the library conservatively accepts at most 12 native frames, all with a common 200–25500ms delay in 100ms steps. These are source-backed compatibility bounds, not measured universal firmware capacity. Native RGB444 truncation is intrinsic to the Mini format, not permission for additional lossy adaptation.

## Public behavior and adaptation

`GIFAnimationLoader.load(path:resize:model:)` composites source disposal/transparency before nearest-neighbor scaling to the chosen model. Default public parameters remain Evo/16×16. Mixed-model frames and encoding a frame with the wrong selected model fail before writes. CLI model resolution precedes GIF conversion; the REPL uses its current target model on every command.

`TimeboxAnimationEncoder.prepare(_:model:adapt:)` and `TimeboxClient.send(animation:adapt:)` produce native Mini packets when explicitly selected/resolved. Ordinary usage remains `timeboxctl animation art.gif --device mini`, with optional `--resize fit|fill|stretch` and `--adapt`. All packets are prepared before connecting; a partial one-shot upload is not retried.

Without adaptation, timing is preserved exactly when a common supported delay can represent every hold within 12 slots. Repeated identical native frames are allowed to represent longer holds without losing images or duration; source/effective frame counts report this expansion, but `adapted` stays false. An unrepresentable input fails instead of silently clamping or thinning.

With `--adapt`, candidates are common delays from 200 through 25500ms in 100ms steps with 2–12 frames. The planner minimizes total-duration error, then prefers more native frames. It samples the original timeline uniformly at those frame starts. Structured output and stderr report source/effective counts and total duration, the common delay, and semantic changes (`temporal_sampling`, plus `timing_rounding` when needed). Inputs longer than 12×25500ms still fail. Adaptation may remove intermediate images and change timing; geometric fitting never implicitly enables it.

## Independent automated evidence

[Packet fixtures](fixtures/mini-animation-red-green.hex) were generated by executing only the pinned reference's pure frame-packing/framing methods, without its imports, radios or assets. [Reference metadata](fixtures/mini-animation-reference.json) records commit and source hashes. The original [11×11 red/green GIF](fixtures/mini-red-green-500ms.gif) uses 500ms per frame. Its exact reference packets are 195 and 196 escaped wire bytes (391 total). The additional byte in frame 1 is its escaped index.

Tests cover exact fixtures, GIF dimensions, unchanged Evo output, mixed-model rejection, the 12-frame boundary, lossless repeated holds, static-single-frame reporting, explicit sampling/timing changes, saved/current model routing, failed preflight without connection, partial write failure, library sends and continued Mini text rejection. No hardware access was performed by the implementing agent.

## Physical validation pending

First parent-owned test: `timeboxctl animation docs/validation/fixtures/mini-red-green-500ms.gif --device mini --model mini --json` (or a paired address with explicit Mini model). The controller should observe red then green for approximately 500ms each and determine repetition and disconnect behavior. A persistent REPL comparison is useful because the Mini can show a Bluetooth status symbol after connection loss. No timing accuracy, 12-frame capacity, persistence, frame replacement, unequal-delay behavior or 100ms minimum is claimed before physical evidence.

## Mini scrolling-text follow-up

[AdrieanKhisbe/timebox-studio#18](https://github.com/AdrieanKhisbe/timebox-studio/issues/18) currently promises one-pixel-per-100ms scrolling without text truncation or frame thinning. Even a single glyph needs more than 12 viewport positions at 11×11, and its 100ms cadence conflicts with the conservative 200ms minimum. Therefore Mini `text` remains explicitly unsupported. A follow-up must agree on an intelligible Mini-specific motion/storage contract or establish a streaming method; it must not silently apply GIF sampling to written content.
